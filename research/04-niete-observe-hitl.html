Headline correction before anything else: there is no "three recordings" structure in the code. A NIETE observation has exactly two coach recordings — one classroom lesson recording (awaiting_audio) and one later coach↔teacher debrief recording (awaiting_debrief_audio) — plus an optional photo gate (up to 3 photos) and an optional lesson-plan link. /remark is a separate principal-evaluation feature (bot/shared/handlers/remark-command.handler.js:1-12), not a third observe recording. A grep for "three recording", "segments", "pre/post-lesson" across bot/shared/services/observe and docs/ returns nothing. The build plan should say "after the classroom recording is received" or "after the observation form is submitted" — those are two different moments with different context available (§4).

1.3 The recordings (two, not three)

Recording 1 — the classroom lesson. Any audio from a leader-family user goes through the single router bot/shared/services/observe/observe-audio-router.js:101-190. Both entry points feed it: voice notes (whatsapp-bot.js:2568-2569) and audio documents (:2490-2491, :2517-2518) — a phone-recorder app delivers a 40-minute lesson as a file, and Meta's limits differ (voice 16 MB, document 100 MB: whatsapp-bot.js:2426-2427, bot/shared/services/whatsapp.service.js:885-886). The webhook never carries a duration, so the router probes it itself (getMediaInfo → ffprobe, :41-60). "Classroom-length" = ≥900 s, or unresolvable-but-≥500 KB (:34-35, :114-116).

Decision table (:137-189): state awaiting_audio → ObserveCapture.startFromAudio; state awaiting_debrief_audio → startDebriefFromAudio; nothing armed + declared self-coaching intent → falls through to DC (:169-174, row-122 fix); nothing armed + classroom-length → park and ask "whose observation is this?" (observe-binding.service.js:59, FIFO cap 3, TTL 6 h, sha-dedupe 24 h: :29-32). Invariant: a leader's classroom-length audio never starts teacher coaching.

startFromAudio (bot/shared/services/observe/observe-capture.service.js:56-142) inserts the coaching_sessions row directly at status='confirmed' (no Yes/No confirm), observation_type='leader_observation', observer_user_id=coach, user_id= bound teacher's uuid when bound else the coach (:73-87), queues transcription (:100-101), retires the matching observation_schedules row (:106-113), clears the Redis slot so the next recording is bindable (:120), acks (:121), and if unbound fires the non-blocking "who did you observe?" list (:129-136, observe-who.service.js, which writes an observation_schedules row with session_id rather than a new table :17-25, :111, :225).

Recording 2 — the debrief (coach talking with the teacher after the form). Armed by startDebrief (observe-debrief.service.js:412-497), captured by startDebriefFromAudio (:532-580), processed by the observe_debrief job (:740-875). Detail in §2.4.

Optional gates between recording 1 and analysis: when OBSERVE_CAPTURE_GATES_ENABLED=true the coach gets the photo gate (≤3 photos, classroom-photo/capture.service.js:52) and the LP-link gate, addressed in the coach's language (transcription-processor.service.js:373-404); flag off → analysis queued directly (:377-383).

2. The HITL edit step

2.1 Mechanics

Endpoint POST /api/flows/observe-mewaka (bot/shared/routes/flow-endpoint.routes.js:139-158; legacy name, path generic) → handleObserveMewakaRequest (bot/shared/routes/observe-mewaka-endpoint.js:84-145). Token → session ownership check (:46-58). INIT serves the pack's first screen prefill (:93-102); BACK re-serves prefill (:104-112); each data_exchange buffers that screen's r_/ev_/imp_/fid_ fields in Redis observe:edits:<sessionId> (TTL 2 h, :26-27, :61-78); the last screen's submit calls applyObserverEdits and returns SUCCESS with extension_message_response.params.observe_action='submitted' (:119-131). Redis loss degrades to "no edit recorded" for lost screens (:11-14). Contract: never return version; every key must be declared on the screen (:4-6).

2.2 Return path

The nfm_reply webhook carries observe_action → bot/shared/utils/flow-type-detector.js:110-111 → 'observe' → whatsapp-bot.js:1887-1910: send submitted_ack, clearStateAfterSubmit (guarded so a live debrief for another session is not clobbered, observe-debrief.service.js:360-373), then the Debrief now / later buttons (buildDebriefChoiceButtons :71-81).

2.4 Debrief (recording 2) and coach-the-coach

startDebrief (observe-debrief.service.js:412-497): builds a 6-step guide from v2 with GPT5MiniService.completeJson (:455-458; gpt5-mini.service.js:646-661, the helper whose absence once produced "completeJson is not a function" on 0/48 debriefs — :650), validates, falls back deterministically, arms awaiting_debrief_audio {sessionId, guide_snapshot} (:489-491). startDebriefFromAudio (:532-580) merge-writes analysis_data.observer_debrief = { audio_id, audio_mime, guide_snapshot, recorded_at, transcript:null, … attempts:0 } (:555-568) and queues observe_debrief — never queueTranscription, whose processor would overwrite the lesson transcript (:526-530). processDebriefRecording (:740-875): downloads the WhatsApp media, transcribes with DEBRIEF_ROLES (coach/teacher, :797-812), persists the transcript before the LLM pass (:829-834), generates feedback (:843-857), delivers praise + rendered card (_deliverCoachFeedback :582-620) and flips debrief_status='done' (:612). Transcription failure is recorded on the row and retried by the sweep, not by SQS (:813-821).

7. Gotchas a build plan must respect

  1. Repo and branch. NIETE-Rumi is its own codebase and Railway project; develop is staging and nothing reaches main without passing through it (root CLAUDE.md Rule 7; NIETE-Rumi/CLAUDE.md:12). Worktree per bead (Rule 21).
  2. Presence-based feature gating. Every observe capability is a Flow id in env: OBSERVE_MEWAKA_FLOW_ID (form; also the master switch observe-gate.js:62), OBSERVE_VISIT_FLOW_ID (picker), OBSERVE_FRAMEWORK=fico, OBSERVE_FICO_FLOW_HAS_FIDELITY (value-aware because published Flows are immutable, observe-draft.service.js:278-285), OBSERVE_CAPTURE_GATES_ENABLED, OBSERVE_SCHEDULING_UI, OBSERVE_STAGE_SCREENS. Read at call time, not import (observe-command.handler.js:26-33). A new STUDENT_ASSESSMENT_FLOW_ID follows the same rule.
  3. "Code ported but the dependency wasn't." completeJson was missing in this fork and killed 0/48 debriefs (gpt5-mini.service.js:646-651); leader_schools/observation_schedules shipped as migrations but were absent from 00_complete-schema.sql, so a fresh bootstrap silently had no visit planning (schema :4592-4598). The observe columns are still missing from the schema file (tests/baseline.snapshot.json:116-120). Ship schema + migration + code in one PR; the column-completeness guard must not grow.
  4. WORKER_QUEUES. Per-service queue subsets (sqs-worker.js:134-181, :1366-1381); main worker main,quiz, video worker video (root change log, Aug 1–3). A new job type must be routed to a queue a live service polls, and the boot log must show it.
  5. Pre-merge classes O/P/Q (.claude/skills/pre-merge-checklist/SKILL.md:49-51): O — a test that jest.mock()s the module whose return value is under audit proves nothing; P — setInterval in a service that redeploys faster than the interval (every sweep here is on the always-on worker; add a boot-time run like runDebriefRetrySweep :1282-1285); Q — a capability with no caller (new exported function or table-driven flow entry must be wired, e.g. every list-row prefix needs a dispatch branch in whatsapp-bot.js or taps die "Unknown list item ID", observe-debrief.service.js:6-8). Class R (DB load) for any worker query.
  6. Flow contract. Never return version; every returned key must be declared on the screen; ~10 s Meta timeout so the endpoint only reads pre-computed drafts (observe-mewaka-endpoint.js:4-9); a Meta Flow is a DAG with one Footer per screen — loops are close-and-reopen (observe-command.handler.js:87-95); WhatsApp caps: list ≤10 rows, button title ≤20 chars, TextArea 600 default, TextBody 4096 (observe-debrief.service.js:36, :66-69, observe-draft.service.js:23-28, :91). Token formats: picker user.id (no colons), form observerId:sessionId.
  7. Row-derived, never payload-derived. Observe-ness comes from observation_type on the row; the recipient comes from the row not the job's from (bd-wwcgf, observe-draft.service.js:368-391); SQS payload loss is a known class (bd-1525). Every new job must be re-runnable from the row alone.
  8. Never clobber another session's live state. armDebriefAudio/clearStateAfterSubmit/onAnalysisReady all refuse to overwrite an awaiting_debrief_audio for a different session (observe-debrief.service.js:360-398, observe-draft.service.js:356-366). A per-child loop adds a third contender for the one Redis slot — design the key so it cannot race the debrief.
  9. Language. observeLang(user) + per-language string packs (observe-strings.js), one writer for preferred_language, code-point caps (root Rule 20). The sw ? sw : en collapse that turned Urdu coaches English is the documented failure (observe-debrief.service.js:760-765).
  10. Media lifetime. Meta media ids expire ~30 d; the debrief path stores only the id and has a 28-day retry ceiling as a result (debrief-retry-sweep.js:30-31). Upload child audio to R2 at intake.
  11. Testing. Root npm test is a delta gate against tests/baseline.snapshot.json (CLAUDE.md:41-52); bot-only deps must be stubbed in tests/__mocks__/; 10 observe suites at tests/observe/, 110 more at bot/tests/observe/. Red-first (Rule 6).
