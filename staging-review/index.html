EGRA Test Build Review

Sabeena's EGRA/EGMA test flow on the main Rumi bot's staging server, read against the plan we wrote for a five-minute, coach-run, AI-checked child assessment. What is done, what is not, what falls short, and what was done well.

The answer in one minute

Which bot. It is the main Rumi bot, not the NIETE bot. All eight commits are on the staging branch only, behind a switch that is on for staging and limited to Islamabad test accounts. Nothing has reached production.

What it is. A careful, well-documented first build that puts almost the whole May 2026 enumerator test into WhatsApp chat. The coach taps Correct or Incorrect for every item, one message at a time. No AI is used anywhere, and a database rule stops an AI score from ever being stored.

How it compares with the plan. It builds a different product. The plan is a five-minute test: the coach records one voice note per block while the child reads from a printed card, Rumi pre-fills a checking form, and the coach corrects it. This build takes about 22 minutes per child, which is today's enumerator time, and the one-message-per-item pattern is the one the field team rejected on 11 September.

Does it work today. Not end to end. The test pictures never reach the coach, and the one subtest with audio would lose the coach's marks when it saves. No real child has been assessed yet: across 9 staging sessions, one subtest result was ever saved.

What to keep. The item bank, the code-drawn stimulus pictures, the random draw from the real roster, the switch-and-region gate, and the chat-loop fix are all good foundations for the plan's version.

Fix these first

These are small fixes, and each one matters before a real child is tested. The first touches the database production shares, so it needs a go.

  1. The results table is open to the public key. Row-level security is off, and the public anon and authenticated roles can read, insert and delete rows. The table lives in the database that production shares, and it already holds one child's name. Switching on row-level security fixes it; the bot uses the service key, so nothing breaks. needs a go: production database
  2. No stimulus picture can be delivered. All seven picture links point at the private storage address, which refuses the download (HTTP 400). The three real attempts, on 19, 21 and 24 September, all failed. The code only falls back to text when no link exists, not when the send fails, so the coach gets a bare "Ready? Start" button with no letters, no story and no timing rules.
  3. The listening subtest would lose the coach's marks. The save always includes the voice-note fields, but those columns were never added to the live table. The database rejects the whole row, and the coach still sees "Assessment complete". It has not happened yet only because no tester got past the voice-note step.
  4. The letter score subtracts errors twice. The code computes (correct − incorrect) per minute, where "correct" already excludes errors. A child with 34 of 40 right scores 28, and a stopped child can score below zero. A test expects the negative number.
  5. Any Islamabad teacher can list every Islamabad class. Access is checked by region only, and 53 of the 56 Islamabad users are teachers. Any of them can type /egra, see every class and receive a random child's full name.

What was done well

Safe to run dark

Off by default, limited to Islamabad accounts, inert for everyone else, with tests proving it. TESTING.md lists its own gaps honestly, including the class-choice bias.

Real test content

The fielded EGRA/EGMA item bank was recovered with answer keys, built by script and checked by tests. It is the most reusable piece of the branch.

Pictures drawn by code, not AI

Stimulus images are rendered from the exact item text, in a correctly embedded Nastaliq font, right to left, and checked back against the item bank. Using AI image generation for test items would have been wrong; this was the right call.

A real random draw

The coach no longer types a name. The child is drawn on the server, uniformly, from the real roster. That is a genuine step toward "the coach does not choose".

Audio handled with discipline

The voice note goes to our own private storage straight away, not left as a WhatsApp media ID that expires. Correctly, no audio is assumed inside the Flow.

Careful routing, good debugging

Flow completions are matched to the right session; the voice claim only fires in the right step. The chat-loop fix was traced in the logs to its real cause, with a failing test written first.

Time per child

The estimate walks the code message by message for one child: 113 bot messages and 96 coach actions (83 taps, 11 typed answers, 2 voice notes). The time with the child comes from the May enumerator medians for the same 14 subtests (13.8 minutes). WhatsApp round trips, typing wrong-item lists and re-asking questions for the voice note add the rest.

Architecture and code

The code is organised sensibly: small single-purpose services, a gate, a state machine in one handler, and switches that keep it inert. The problems are in the edges: what happens when a send or save fails, what the tests fake, and a few formulas.

  • Failures are silent. A failed picture send and a failed save are both ignored. The coach is told everything worked, and the lost data cannot be recovered from the logs.
  • The tests cannot see the real failures. WhatsApp sends and database saves are faked to always succeed, and picture links are only checked for their shape. The voice-routing test searches the source text, and the Flow-response test covers a function nothing in production calls. All 132 tests pass while the build cannot complete a child.
  • Scoring does not follow the instrument. Beyond the letter formula: the English story counts full stops and commas as words (+13% for a child who finishes); there is no 60-second cap; the Discontinue button marks the first ten items wrong on every grid, including the stories, which have no such rule; comprehension has no "not asked" option and is asked even when the child read nothing.
  • Answers can land on the wrong question. Correct/Incorrect buttons do not say which item they belong to, so a double tap or a tap on an older message is recorded against the current item.
  • Coaches can get stuck. /cancel becomes the child's name at the name prompt and "not a number" at the typed prompts. Other commands are swallowed for up to an hour. The voice note cannot be skipped.
  • Children's audio and names can leak into general chat. A voice note sent outside the exact voice-note step goes through the normal pipeline: transcription, the conversations table, and the chat model.
  • A shared prompt was changed for every region. The chat-loop fix edits the general-chat prompt all regions use. It is a good fix for Pakistan, but it points Palestine teachers to a /reading test that is disabled there, and Tanzania teachers to the English test.
  • Data hygiene. One real tester phone number is committed in the test file. The roster query pulls every Islamabad child's name just to count them.

Coach experience

  • Everything the coach reads is in English, hard-coded, including the Flow. Islamabad coaches work in Urdu, and our checking-form draft and the observation form are Urdu.
  • Two instructions would invalidate the reading subtests. "You will read out each item to the child" and "or read it out per the item type" would have the coach read letters and words aloud for the child.
  • No answer key is shown. Every item has one in the item bank, but no code sends it, so each coach decides what counts as right.
  • The listening steps are in the wrong order. The child answers inside the Flow, and only afterwards is the coach asked to record "the child's response". The recording either repeats the questions or holds nothing useful.
  • No sense of progress. The coach sees "Item 3/8" but never "subtest 6 of 14" or how much of the session is left, and gets no "child 2 of 5".
  • The end result is a text list of raw per-subtest scores, only if all 14 subtests are finished. There is no level, no benchmark, nothing for the teacher and no class view.

Design of the child's card

The pictures are well made as images: clean, correct Unicode, correct Nastaliq joining and right-to-left order. The problem is what they are designed as. They are the enumerator's score sheet, shown to the child on the coach's phone.

  • Every item carries a printed number. A real EGRA child card has none; numbers belong on the assessor's sheet.
  • The stories are cut into numbered word boxes, so the child is not reading connected text, and the result is not an oral reading fluency measure. Punctuation gets its own box.
  • The print is small on a phone. English story words are about 2 mm tall with the phone turned sideways, and 1.1 mm upright. On a printed A4 card each of the ten columns gets about 27 mm; on the phone it gets about 6 mm.
  • One phone cannot be the child's card and the coach's score sheet. The coach has to hold the phone up, keep time with no clock, remember which of up to 100 items were wrong, then take the phone back to tap Stop and type the numbers. The plan's printed card avoids all of this.

Randomization

What the call decided. The impact team's algorithm names the children from the class register; the coach never chooses. Each pick comes with named alternates for absent children (the Usser study took odd roll numbers and replaced an absent child with the next even number). Five children per visit.

The right way to do it

  1. Draw once per measurement cycle, on the server, before anyone sees a name. A cycle is one quarter, since the call recommends EGRA every three months. Snapshot every active child in the target grades at each school.
  2. Shuffle each class once, with a secret seed made from a key, the class and the cycle. Save every child's rank. The secret stops anyone predicting the order; saving it lets us re-run the shuffle for an audit.
  3. At each visit, send the next five in rank order, with roll numbers, plus the next two or three as named alternates, in one WhatsApp list.
  4. Absence is a reason, not a redraw. The coach taps absent, refused, left school or similar; the next alternate moves up. An absent child goes back in the queue and is tried again at the next visit before being marked absent for good.
  5. No redraws and no typed names in the coach's path. Reopening shows the same list. A manual entry, if kept at all, is for supervisors, needs a reason, and is left out of outcome figures.
  6. Record each child's chance of selection (class size at the draw), so regional figures can be weighted. Small classes are tested in full.
  7. Make "5 new" versus "3 new + 2 repeat" a setting, so the draw does not change when that decision is made. Repeat children come from the top of the previous cycle's random order, so they are random too.
  8. Reuse what exists. student-selection.service.js, already on staging, orders never-tested children first, picks several at once, checks attendance and labels roll numbers. It needs a seeded shuffle instead of Math.random, a saved order, and alternates with reason codes.
What the numbers can detect. About six visits per school per quarter at five children each gives 30 tests, or 15 in each of two classes. That is the right amount per class, but a 0.2 standard-deviation change becomes visible only across about 100 classes with new children, or about 20 classes if the same children are retested. A month-to-month change needs whole-class testing. These figures rest on assumed clustering and retest correlation; treat them as orders of magnitude.
